# 캠페인 테이블 성능 메모

현재 리팩토링에서 늘어난 객체 생성 자체는 큰 성능 이슈로 보지 않는다. 대부분은 렌더 시 생성되는 얕은 객체이고, 하위 컴포넌트도 `React.memo`로 최적화된 상태가 아니다. 따라서 지금 단계에서는 유지보수성을 우선하는 방향이 적절하다.

## 개선 포인트

1. `useCampaignTableSelection`의 선택 판정
   - 현재는 `filter`와 `includes` 조합으로 보이는 선택 상태를 계산한다.
   - 행 수가 커지면 `O(n*m)` 비용이 커질 수 있다.
   - 개선 방안: `selectedRowIds`를 `Set`으로 보조 관리하거나, `selectedRowIdSet`을 파생값으로 만들어 반복 검색 비용을 줄인다.

2. `CampaignTableTable`의 row 렌더링
   - 각 렌더마다 row 배열과 checkbox JSX가 새로 만들어진다.
   - 현재 규모에서는 문제 없지만, 데이터가 늘면 렌더 부담이 커질 수 있다.
   - 개선 방안: row 컴포넌트를 분리해 `React.memo`를 적용하고, 선택 여부는 `Set` 기반으로 계산한다.

3. `useCampaignTableViewModel`의 파생 배열 생성
   - `visibleRowIds`와 상태 묶음 객체가 렌더마다 생성된다.
   - 현재는 비용이 작지만, 데이터가 더 커지면 불필요한 파생 계산을 줄이는 편이 좋다.
   - 개선 방안: 결과가 실제로 바뀔 때만 갱신되도록 `useMemo` 또는 내부 훅으로 파생 로직을 이동한다.

4. 하위 UI props 묶음
   - `toolbarState`, `tableState`, `dialogState` 같은 객체는 구조를 단순화하는 데 유용하다.
   - 다만 나중에 자식 컴포넌트를 memoize할 경우, 이 객체들 때문에 참조가 매번 바뀔 수 있다.
   - 개선 방안: memo가 필요한 시점에만 `useMemo`를 도입하거나, 성능 민감한 경로는 primitive props로 유지한다.

## 우선순위

- 1순위: 행 수 증가가 확인되면 `selection` 계산을 `Set` 기반으로 변경
- 2순위: 표가 커지면 row 컴포넌트 분리 및 메모화 검토
- 3순위: 실제 프로파일링에서 파생 배열이 눈에 띄면 `useMemo` 도입

## 현재 판단

지금 상태에서는 성능보다 구조 단순화의 이점이 더 크다. 즉시 최적화가 필요한 수준은 아니고, 데이터 규모가 커질 때만 위 항목들을 순차적으로 적용하면 된다.
