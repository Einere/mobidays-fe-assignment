# 3.3 캠페인 관리 테이블 설계

## 배경

`docs/mobidays_fe_assignment_guide.md`의 `3.3 캠페인 관리 테이블`은 전역 필터 결과를 캠페인 단위로 요약해서 보여주는 검토형 위젯이다. 사용자는 필터링된 캠페인 목록을 비교하고, 검색과 정렬로 필요한 대상을 좁힌 뒤, 선택한 캠페인의 상태를 신중하게 변경할 수 있어야 한다.

현재 코드베이스에는 다음 기반이 이미 존재한다.

- 전역 필터 atom과 `useDashboardData(filter)` 기반 조회 흐름
- MSW 기반의 브라우저 메모리 데이터 소스
- 테이블 로컬 상태 초안인 `useCampaignTableControls`
- 공용 `DataTable` 컴포넌트

따라서 이번 작업은 새로운 조회 진입점을 만들기보다, 기존 조회 결과 위에 테이블 전용 뷰모델 레이어와 검수형 상호작용을 추가하는 방향이 가장 자연스럽다.

## 목표

- 전역 필터와 동기화되는 캠페인 관리 테이블을 제공한다.
- 테이블 전용 뷰모델을 도입해 계산, 포맷, 예외 처리를 UI에서 분리한다.
- 검색, 정렬, 페이지네이션, 선택 상태를 모두 테이블 로컬 상태로 관리한다.
- 일괄 상태 변경은 MSW 메모리 스토어를 갱신하고 React Query 재조회로 반영한다.
- 검토 우선 UX를 적용해 실수 가능성을 낮춘다.
- 모바일에서도 카드형으로 전환하지 않고, 압축된 표와 가로 스크롤로 검토 맥락을 유지한다.

## 비목표

- `3.4 캠페인 등록 모달`과의 동기화 설계
- 신규 캠페인 생성 흐름
- 선택 과제 위젯 구현
- 실제 영속 저장소 연동
- 서버 측 검색/정렬/페이지네이션 API 추가

## 책임 경계

이번 설계의 핵심은 전역 필터와 테이블 로컬 상태를 섞지 않는 것이다.

- 전역 필터: 어떤 `campaigns`, `dailyStats`를 조회할지 결정
- 테이블 뷰모델: 조회된 결과를 캠페인 행 단위로 요약
- 테이블 로컬 상태: 검색어, 정렬, 페이지, 선택 상태
- 상태 변경 mutation: MSW 메모리의 `campaigns` 상태를 갱신

검색은 과제 명세대로 테이블에만 적용되며, 전역 필터나 다른 차트에 영향을 주지 않는다. 반면 일괄 상태 변경은 `campaigns` 데이터 자체를 바꾸는 작업이므로, 성공 시 재조회된 결과를 통해 테이블이 다시 렌더링되어야 한다.

## 설계 원칙

### 1. 조회와 표현 후처리 분리

조회 책임은 계속 `useDashboardData(filter)`가 가진다. 테이블은 별도 API를 만들지 않고, 조회 결과를 입력으로 받아 뷰모델을 생성한다.

### 2. 뷰모델 우선

API 응답을 JSX에서 즉흥적으로 계산하지 않는다. 지표 계산, 날짜 포맷, 상태 라벨, `null` 표현은 모두 테이블 전용 뷰모델 생성기에서 정규화한다.

### 3. 검토 우선 UX

이 테이블은 빠른 대량 조작보다 실수 없는 변경이 중요하다. 따라서 일괄 상태 변경은 즉시 반영하지 않고, `선택 -> 상태 선택 -> 적용 -> 확인 다이얼로그 -> 확정` 흐름으로 고정한다.

### 4. 모바일에서도 표 문법 유지

모바일에서는 카드 리스트로 완전히 바꾸지 않는다. 비교와 검토가 핵심인 위젯이므로, 압축된 컬럼 폭과 가로 스크롤을 허용해 표 문법 자체를 유지한다.

## 사용자 흐름

1. 사용자가 전역 필터를 조정한다.
2. `useDashboardData(filter)`가 필터링된 `campaigns`, `dailyStats`를 반환한다.
3. 테이블 전용 뷰모델 생성기가 각 캠페인의 집계 지표를 계산해 `CampaignTableRow[]`를 만든다.
4. 사용자는 테이블에서 검색, 정렬, 페이지 이동으로 필요한 대상만 검토한다.
5. 사용자가 행을 선택하고 변경할 상태를 고른 뒤 `적용`을 누른다.
6. 확인 다이얼로그에서 선택 건수와 대상 상태를 다시 확인한 뒤 확정한다.
7. mutation이 MSW 메모리 스토어의 캠페인 상태를 갱신한다.
8. 성공 시 관련 query가 재조회되고, 테이블은 최신 상태로 다시 렌더링된다.

## 데이터 흐름

### 입력

- `DashboardData.campaigns`
- `DashboardData.dailyStats`

전역 필터는 이미 적용된 상태라고 가정한다. 테이블은 이 결과에 대해 추가 검색과 정렬만 수행한다.

### 출력

테이블 렌더링의 canonical input은 `CampaignTableRow[]`다.

```ts
interface CampaignTableRow {
	id: string;
	name: string;
	status: "active" | "paused" | "ended" | null;
	platform: "Google" | "Meta" | "Naver" | null;
	startDate: string | null;
	endDate: string | null;
	periodSortValue: number | null;
	cost: number | null;
	ctr: number | null;
	cpc: number | null;
	roas: number | null;
}
```

실제 구현에서 필드 이름은 일부 달라질 수 있지만, 아래 의미는 유지해야 한다.

- 정렬과 계산에 필요한 원시 값을 우선 보존한다.
- `0`과 `null`을 구분한다.
- 문자열 포매팅은 row 상태로 저장하지 않고, 셀 렌더러 또는 공용 포맷 함수에서 처리한다.

## 뷰모델 계산 규칙

### 캠페인 단위 집계

각 캠페인 row는 해당 캠페인 ID에 속한 `dailyStats`만 합산 대상으로 사용한다.

### 총 집행금액

`cost`의 유효한 숫자만 합산한다.

- 유효 숫자가 하나 이상 있으면 합계 사용
- 유효 숫자가 하나도 없으면 `null`

### CTR

```ts
(총 clicks / 총 impressions) * 100
```

- `impressions` 분모가 0이거나 유효하지 않으면 `null`
- 유효 숫자가 있더라도 분모가 0이면 `null`

### CPC

```ts
총 cost / 총 clicks
```

- `clicks` 분모가 0이거나 유효하지 않으면 `null`

### ROAS

```ts
(총 conversionsValue / 총 cost) * 100
```

- `cost` 분모가 0이거나 유효하지 않으면 `null`
- `conversionsValue`가 모두 `null`이면 `null`

### 기간 표시

집행기간 문자열은 row에 저장하지 않고 셀 렌더러에서 생성한다.

- 기본 표시는 `시작일 ~ 종료일`
- `endDate`가 `null`이면 `시작일 ~ 진행 중`
- 날짜 문자열이 유효하지 않으면 `-`

### 상태/매체 표시

- 상태 라벨과 tone, 매체 라벨은 row에 중복 저장하지 않고 셀 렌더러에서 매핑한다.
- 상태 tone은 현재 디자인 토큰 체계에 맞춰 의미 기반으로 매핑한다.
  - `active` -> success
  - `paused` -> warning
  - `ended` -> neutral

### `0`과 `null` 표현

- `null`은 값이 없거나 계산할 수 없음을 의미하므로 셀 렌더러에서 `-`로 표시
- 실제 `0`은 `₩0`, `0%`, `0` 등 메트릭 문맥에 맞는 값으로 셀 렌더러에서 표시

이 규칙은 과제의 `division by zero`, `null safety` 요구사항을 UI가 아니라 데이터 변환 단계에서 일관되게 해결하기 위한 것이다.

## 검색 규칙

검색은 캠페인명에만 적용한다.

- 부분 일치
- 대소문자 무시
- 사용자 입력의 앞뒤 공백 제거 후 비교
- 검색어가 비어 있으면 전체 row 유지
- 검색어 변경 시 현재 페이지는 1로 리셋

검색 결과는 `검색 결과 건수 / 전체 건수`를 항상 함께 표시한다.

`전체 건수`는 전역 필터까지 반영된 row 수를 의미하고, `검색 결과 건수`는 그 안에서 테이블 검색이 적용된 row 수를 의미한다.

## 정렬 규칙

정렬 대상 컬럼은 과제 명세를 그대로 따른다.

- 집행기간
- 총 집행금액
- CTR
- CPC
- ROAS

정렬 상호작용 규칙은 아래와 같다.

- 정렬되지 않은 컬럼 클릭 -> 오름차순
- 같은 컬럼 다시 클릭 -> 내림차순
- 다른 컬럼 클릭 -> 새 컬럼 오름차순
- 정렬 변경 시 현재 페이지는 1로 리셋

세부 비교 규칙은 아래와 같다.

- `null` 값은 항상 마지막
- 숫자 값은 일반 숫자 비교
- 집행기간은 `startDate` 우선, 같으면 `endDate`를 보조 비교
- `endDate === null`은 진행 중 캠페인이므로, 같은 `startDate` 안에서는 종료일이 있는 캠페인 뒤에 배치한다

이번 설계에서는 집행기간 정렬의 1차 기준을 `startDate` timestamp로 고정한다. 이는 사용자 입장에서 "언제 시작한 캠페인인가"가 더 직관적인 기준이기 때문이다.

## 페이지네이션 규칙

- 한 페이지당 10건 노출
- 대상 집합은 검색 + 정렬까지 적용된 결과
- 현재 페이지가 총 페이지 수보다 크면 마지막 유효 페이지로 보정
- 검색어 또는 정렬이 바뀌면 1페이지로 복귀

이 설계에서는 서버 페이징을 도입하지 않는다. 전체 row 집합은 클라이언트에서 가지고 있고, 페이지네이션만 뷰 레벨에서 처리한다.

## 선택 상태 규칙

선택 상태는 `selectedRowIds: string[]`로 관리한다.

- 행 체크박스는 해당 row 선택 여부를 토글
- 헤더 체크박스는 현재 페이지에 보이는 행을 기준으로 전체 선택/해제
- 현재 페이지 일부만 선택되었으면 indeterminate 상태 표시
- 페이지를 넘겨도 선택 상태는 유지

헤더 체크박스를 "전체 검색 결과" 기준이 아니라 "현재 페이지" 기준으로 두는 이유는 검수형 UX에서 선택 범위를 명확히 이해하기 쉽기 때문이다.

## 일괄 상태 변경 UX

### 툴바 노출 규칙

- 상태 드롭다운과 `적용` 버튼은 항상 테이블 툴바에 노출
- 선택된 행이 0건이면 비활성화

항상 보여주는 이유는 기능 발견 가능성을 유지하면서도, 비활성 상태와 선택 건수 표시로 현재 실행 가능 여부를 분명히 전달하기 위해서다.

### 변경 흐름

1. 사용자가 하나 이상의 행을 선택한다.
2. 사용자가 드롭다운에서 목표 상태를 선택한다.
3. 사용자가 `적용` 버튼을 누른다.
4. 확인 다이얼로그가 열린다.
5. 다이얼로그에는 `선택 n건`, `변경 대상 상태`, `취소/확인` 액션이 표시된다.
6. 사용자가 확인하면 mutation을 실행한다.

### 변경 실행 규칙

- 원본 `src/db.json`은 절대 수정하지 않는다.
- MSW 메모리 스토어 안의 `campaigns` 데이터만 갱신한다.
- mutation 성공 후 관련 dashboard query를 invalidate 하여 재조회한다.
- 재조회된 결과로 테이블이 최신 상태를 반영한다.
- 성공 시 선택 상태와 드롭다운 선택값은 초기화한다.
- 실패 시 기존 선택 상태는 유지하고 오류 메시지를 노출한다.

이 설계는 과제의 "원본 유지" 제약을 지키면서도, 브라우저 세션 동안 사용자 상호작용이 실제 데이터 변경처럼 보이게 만드는 최소 구현이다.

## 모바일 정보 구조

모바일에서는 카드 리스트나 확장형 아코디언으로 바꾸지 않는다. 대신 아래 원칙을 따른다.

- 동일한 column schema를 유지한다.
- 표 전체에 `overflow-x`를 허용한다.
- 모바일에서는 셀 padding과 typography를 한 단계 압축해 한 화면에 더 많은 비교 맥락을 남긴다.
- 선택, 캠페인명, 상태, 매체는 우선적으로 읽히도록 유지하고 나머지 지표는 가로 스크롤로 확인하게 한다.

이 방식은 구현 복잡도를 늘리지 않으면서도, 대시보드 사용자가 기대하는 표 기반 비교 경험을 유지한다.

## 상태별 처리

### 로딩 상태

- 테이블 높이를 유지하는 스켈레톤 또는 placeholder 사용
- 헤더와 툴바는 유지해서 레이아웃 점프를 줄인다

### 재조회 상태

- 기존 테이블 데이터는 유지
- 툴바 또는 보조 텍스트에서 "동기화 중" 상태만 표시

### 오류 상태

- 조회 실패 시 오류 메시지와 재시도 문맥 제공
- mutation 실패와 조회 실패는 메시지를 분리한다

### 빈 상태

다음 두 경우를 구분한다.

1. 전역 필터 결과가 0건
2. 전역 필터 결과는 있으나 검색 결과가 0건

두 경우 모두 empty state는 필요하지만, 안내 문구는 원인을 구분해야 한다.

## 테스트 범위

- `campaigns + dailyStats`로부터 올바른 `CampaignTableRow[]`가 계산된다
- `cost`, `CTR`, `CPC`, `ROAS`가 `null`, `0`, division by zero를 안전하게 처리한다
- 검색이 캠페인명에만 적용되고 대소문자/공백 무시 부분 일치로 동작한다
- 정렬이 명세 컬럼에 대해 오름/내림차순으로 동작한다
- `null` 정렬 값이 항상 마지막으로 간다
- 페이지네이션이 10건 기준으로 동작하고 검색/정렬 변경 시 1페이지로 리셋된다
- 헤더 체크박스가 현재 페이지 기준 전체 선택/부분 선택을 반영한다
- 일괄 상태 변경이 확인 다이얼로그 이후에만 실행된다
- mutation 성공 시 재조회 결과가 반영되고 선택 상태가 초기화된다
- mutation 실패 시 선택 상태가 유지되고 오류가 표시된다
- 모바일에서도 카드형이 아니라 표 기반 비교 경험이 유지된다

## 구현 메모

- `useCampaignTableControls`는 계속 테이블 로컬 상태만 담당한다.
- query key는 기존 `createDashboardDataQueryKey(filter)`를 재사용한다.
- mutation은 가능하면 `@tanstack/react-query`의 `useMutation`으로 래핑한다.
- MSW 핸들러에 상태 변경 endpoint를 추가하더라도, 실제 계산과 검증 규칙은 별도 함수로 분리하는 편이 테스트에 유리하다.
- 상태 badge와 숫자 포맷은 기존 디자인 토큰과 텍스트 스타일을 재사용한다.
